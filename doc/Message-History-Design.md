# Message history

New embedded Codex turns use `historyVersion: 2`. A Codex `agentMessage` item
maps to one durable `Message`; its completed item text replaces its streamed
draft. The completion transaction also creates exactly one content outbox row
(`BotMessage.kind = turn_message`, identified by `messageId`). The turn itself
continues to own cancellation, approvals, runtime configuration, and its diff.
Legacy turns, Claude, and remote runners without message events keep the previous
turn-sized replies. A remote runner can opt in by emitting `turn.started` with
`historyVersion: 2` and the message events below.

## Protocol

Validated against TypeScript and JSON schemas generated by Codex CLI 0.154.0:

- `item/started` with `agentMessage` -> `assistant.message.started`.
- `item/agentMessage/delta` -> `assistant.delta` with the original `itemId`.
- `item/completed` with `agentMessage` -> `assistant.message.completed`, with
  authoritative `text` and optional `phase`.
- A `userMessage` item -> `user.message.accepted`. Both lifecycle notifications
  may arrive; `(turnId, backendItemId)` prevents duplicate history messages.
- `turn/start.clientUserMessageId` identifies the initial user message.
- `turn/steer.clientUserMessageId` is the persistent input's `clientRequestId`;
  `userMessage.clientId` correlates the receipt. This is a correlation identifier,
  not a claim that Codex deduplicates repeated submissions.

The source reference is [Codex App Server](https://learn.chatgpt.com/docs/app-server).
Schema generation for subsequent protocol changes:

```sh
codex app-server generate-ts --out /tmp/agentwaypoint-history-schemas/ts
codex app-server generate-json-schema --out /tmp/agentwaypoint-history-schemas/json
```

## Pending inputs

Steering creates `TurnInput` before dispatch. It remains `queued` after the RPC
succeeds and appears above the composer. Only the corresponding `userMessage`
receipt creates formal user history. Requests are serialized within a turn;
repeating a client request ID returns its existing state without dispatching
again. Different IDs with the same text remain separate inputs.

Known dispatch errors become `failed`; ambiguous transport failures, process
restarts, or turn termination before receipt become `unconfirmed`. A late RPC
error cannot overwrite acceptance. Unconfirmed inputs are retained and are not
automatically resubmitted into another turn. Checking delivery retrieves the
durable request state (or submits it with the same ID if the first HTTP request
never reached the API). It does not infer receipt from matching text or from the
assistant's response. Reconstructing a lost receipt from Codex rollout history
is not currently implemented; missing receipts remain explicitly unconfirmed.

## Ordering, replay, and views

All application-created messages receive a session-local `historySeq` within
their creation transaction. Assistant messages reserve their position when
started; user steering receives its position upon receipt. A user receipt during
streaming does not split the already-running assistant item.

The event writer projects message content and outbox state atomically with each
event. Only adjacent deltas from the same item are coalesced. `Turn.runnerCursor`
tracks the upstream sequence independently from the API sequence (which also
contains queue updates and coalesced events). Browser history snapshots include
the API event watermarks, and live events are applied only after that watermark.
An item completion remains authoritative even if its start or deltas were absent.
On interruption, already completed messages are retained and unfinished messages
are closed as `interrupted` with the text received so far.

History supports optional `limit` and `before` cursors; callers that omit them
receive the whole history. The web application loads the complete message
snapshot on session entry/reload and after manual compaction. During a turn,
message lifecycle, receipt, delta, and interruption events update that snapshot
incrementally. New-turn creation, turn termination, cancellation, and legacy
steering calibrate only the affected turn using `history?turnId=...`; these
responses merge by message id instead of replacing older history. This query
validates turn ownership and session membership and includes legacy message
associations. `messageTurn` supplies the requested turn's protocol version and
API event watermark, including after termination, to prevent replaying deltas
already represented in the snapshot.

Chat bubbles use TanStack Virtual with stable message ids and dynamic height
measurement. The render buffer includes at least 12 bubbles and two viewports
(minimum 1200 pixels) above and below the visible range. The list follows new
messages and streaming growth only while pinned to the bottom; reading older
history retains its anchor. Thinking placeholders participate in the same
virtual list. History is no longer sliced or collapsed back to ten bubbles.

The history response does not include the session's full `turns` collection.
`activeTurn` contains only the running turn's runtime information, protocol
version, and API event watermark; `latestTurn` contains the latest turn's runtime
information for the session details. Both are nullable. `activeTurnId` and
`activeTurnStatus` remain available, and `turnCount` supplies the count without
transferring historical turn records. Pending inputs are queried separately so
unconfirmed inputs from ended turns remain available.

Messages carry their own `turnId` for Timeline and Diff requests. Legacy messages
missing the field are resolved from known message associations for the requested
page only; copied history without a source-turn association remains unlinked.

A message's Timeline covers `(timelineStartSeq, endEventSeq]`: activity after
the preceding assistant completion, through the selected assistant completion.
The live view advances at message boundaries and retains following activity.
The full-turn view remains available. Tool output is still addressed by its
turn and stable item/call reference, including tools crossing message boundaries.
Timeline uses an independent TanStack Virtual list with stable event ids and
dynamic height measurement. Its buffer includes at least 12 events and two
viewports (minimum 1200 pixels) above and below the viewport. Appends and output
growth follow the bottom only while pinned; tab changes preserve the scroll
position and measurements for the same turn/message scope. Switching scope starts
at the latest event. Event grouping and the 80ms SSE batch remain independent of
virtual scrolling.
Diff always loads the enclosing turn's `TurnDiffSnapshot` and is labeled as the
entire turn's changes.

## Migration and rollback

`20260917000000_message_history` adds columns and `TurnInput`, backfills only
message order and known turn associations, and preserves legacy text and outbox
state. It does not reconstruct old message boundaries or guess old steer
associations. New and old turns may coexist in the same session. Forked history
copies message text and ordering without retaining references into the source
session's turns/events.

Run the usual `prisma migrate deploy` startup path. Test upgrades against a
database copy first. Keep this reader when disabling v2 writes: an old binary
does not understand the new one-to-many history or input queue. Do not reverse
the migration or delete v2 data as a rollback mechanism.

## Validation

- `message-history.spec.ts`: real SQLite projection, queued input correlation,
  complete snapshots and scoped turn calibration (including legacy links),
  authoritative completion, interruption, pagination, ordering, and replay.
- `message-history-migration.spec.ts`: applies the checked-in migrations to a
  legacy fixture and verifies preserved data, uniqueness, and cascading cleanup.
- `codex-backend.spec.ts`: protocol mapping and correlation fields.
- `history-messages.spec.ts`: browser state reduction and response/receipt races.
- `apps/web/e2e/history.pw.ts`: real web/API/SSE with a controlled runner,
  covering queued input, reload, streaming, message Timeline, turn Diff,
  compaction activity, legacy completion, full snapshot/scoped transfer,
  virtual overscan, reading anchors, panel restoration, and viewport resizing.

The browser test requires a web production build and installed Playwright
Chromium; all test data and listeners are temporary. It does not call a live AI
backend or access the live AgentWaypoint home.
